Phase 1 (second half): production, deliveries, invoices, payments, dashboard, admin

End-to-end the catering flow now runs from order intake all the way to PAID
and into the audit log. The remaining Phase-1 spec items — Quotes module +
PDF rendering — are deferred to Phase 1.5; everything else from the
operational spec is in.

Library additions
- src/lib/sequences.ts: nextProductionJobNo, nextDeliveryNumber.
- src/components/ik/Sidebar.tsx: FY label is now computed via istFyLabel()
  instead of hardcoded "FY 25-26" (caught during a browser walk of the
  first-half UI). Same TODO refactor note (over 250-line component cap)
  remains.

Modules

- Production Jobs + Kitchen Board (server actions: createProductionJobForOrder
  (internal helper), assignChef, startProductionItem, markProductionItemReady,
  listProductionJobs, getProductionJob, listChefs). The first item starting
  cascades the job to PREP; all items READY cascades the job to READY and
  the order to READY. Auto-creation is wired into chef-requisitions'
  issueChefRequisitionLine path so when every requisition for an order is
  FULLY_ISSUED, the order auto-advances to READY_FOR_PRODUCTION AND a
  ProductionJob (+ items) is created idempotently. UI: /kitchen 4-column
  kanban (QUEUED / PREP / COOKING / READY) with today/tomorrow/thisweek
  pills; /kitchen/[id] item table with chef-assign + Start + Mark ready
  actions.

- Deliveries (scheduleDelivery generates a 4-digit OTP, bcrypt-hashes it,
  logs plaintext to server console for Phase 1; dispatchDelivery, markArrived,
  confirmDeliveryOTP with 3-attempt lockout + DeliveryAttempt rows, failDelivery,
  listDeliveries, getDelivery, listDrivers). PII guards: DELIVERY role only
  sees their own deliveries' phone/address (SECURITY.md §6). Web UI:
  /deliveries list, /deliveries/new schedule form, /deliveries/[id] timeline +
  driver controls (Dispatch / Mark arrived / OTP confirm / Mark failed).

- Customer Invoices (no IRN; Phase 3 wires e-invoicing). createCustomerInvoiceFromOrder
  copies OrderItems → CustomerInvoiceLines, computes GST split (CGST+SGST
  intra-state vs IGST inter-state) via existing lib/gst.ts summarise().
  issueCustomerInvoice flips DRAFT → ISSUED and cascades the order to INVOICED.
  cancelCustomerInvoice with reason. listCustomerInvoices, getCustomerInvoice,
  getCustomerInvoiceByToken (token-gated public view, no auth). UI:
  /invoices list, /invoices/[id] with line items + GST breakdown + payments
  table + Cancel form, /i/[token] public-facing invoice view (24-byte
  base64url token; URL contains no PII).

- Payments (recordCustomerInvoicePayment + reverseCustomerInvoicePayment).
  Atomic: creates payment row, recomputes amountPaid from non-reversed
  rows, flips invoice status ISSUED → PARTIAL → PAID. PAID invoices
  cascade the order to PAID; reversals demote the order from PAID back
  to INVOICED. /payments → /payments/receivables AR list. AP list
  placeholder noting Phase 2 vendor bills.
  Record-payment form embedded on /invoices/[id] (UPI / CASH / NEFT / RTGS
  / IMPS / BANK_TRANSFER / CREDIT_NOTE / WAIVER / ADJUSTMENT / OTHER /
  CHEQUE).

- Minimal Dashboard (4 KPI tiles: today's orders, today's deliveries,
  outstanding AR, low-stock count) + role-aware "Pending my approval" card
  linking to the appropriate queue:
    STORE_KEEPER  → /queue/store-approvals
    MANAGER       → /queue/manager-approvals
    KITCHEN_HEAD  → /kitchen
    SALES         → /orders?filter=draft (own drafts)
    DELIVERY      → /deliveries (own active)
    ACCOUNTS/ADMIN→ /payments/receivables

- Admin (ADMIN-gated). createUser / updateUser / deactivateUser (rejects
  self-deactivation) with bcrypt cost 12. /admin landing tiles. /admin/users
  list + new/[id] forms (UserForm with create-vs-edit modes; create requires
  ≥8-char password; edit leaves password blank to keep). /admin/settings:
  Settings model CRUD, with type-aware editors (boolean toggle / number
  input / string text / JSON fallback) and an "Add setting" form for new
  keys. /admin/audit: read-only AuditLog viewer with entity + action
  filters, payload-hash truncated for at-a-glance scanning.

Security checkpoint

  install gitleaks). CI scan blocks at PR time when CI lands.
- .env.example: all process.env.* references in src/ documented.
- console.log in src/server/: zero. The OTP plaintext logged from
  scheduleDelivery uses console.error (the SECURITY.md-permitted channel),
  is dev-time only, is short-lived, and the bcrypt-hashed copy in the DB
  is what gates confirmation.

  intentionally-unguarded:

        with a Prisma transaction client; not callable from client RPC.

- No process.env in src/app/.

  driver isn't assigned to; customer phone hidden when role=DELIVERY and
  not the assigned driver (SECURITY.md §6 PII rule).

  Same set tracked in Phase 0.
